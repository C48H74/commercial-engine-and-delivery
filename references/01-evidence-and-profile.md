# 1. Evidence and business profile

> Every deliverable must respect this reference. If this file conflicts with any other, **this one wins**.

## 1.1 The evidence ladder — do not declare "done" before the last rung

| Rung | Meaning | Deliverable example |
|---|---|---|
| 1. **Exists** | there is an artefact | "the email was written" |
| 2. **Substantial** | has real content, not placeholders | "has offer, price and next step" |
| 3. **Connected** | tied to what the client said | "uses the words and the number they gave" |
| 4. **Functional** | has been tested or used for real | "the client replied / the number was verified" |

**Practical rule:** when you deliver, state the rung. Never present rungs 1–3 as if they were 4.
A well-written plan (3) is not a plan that works (4).

## 1.2 How to handle numbers

| Source of the number | What to do |
|---|---|
| The client's own document | cite the source and date |
| Public report (e.g., PMI Pulse) | cite report, year and page |
| Your own estimate | write **"Estimate"** next to it |
| Not found | write **"Not found"** — never round to a plausible number |
| User's own metric, testimonial or case | leave `[to fill in]` — **never invent** |

**Contradiction rule:** if a new number contradicts one stored in the profile, **update the profile** and tell the user. An outdated profile contaminates every later deliverable.

**Numbers that circulate without a source** (do not repeat): "35% of projects fail due to inadequate scope", "detailed planning has 2.5x more success", "mature organisations in cost are 45% more efficient". If there is no identifiable report, **do not use the number**.

## 1.3 The trust and evidence cycle

```
1. Quantify the pain  →  2. Promise only what you control
        ↑                              ↓
6. Win the next "yes"        3. Show evidence
        ↑                              ↓
5. Measure and review  ←   4. Deliver fast (TTFV, 30/60/90)
```

Trust compounds: each step reduces the risk perceived by the buyer. It is a loop, not a stage.

### Trust withdrawals — never make these
❌ invented urgency · ❌ false scarcity · ❌ case study without the client's permission · ❌ simulation presented as a client result

### Trust deposits
✅ scheduled next step · ✅ written scope · ✅ honest "not for you" section · ✅ only real deadlines · ✅ say out loud what you do **not** do

## 1.4 Promise only what you control

| You control | You **do not** control |
|---|---|
| the process, the method, the delivery deadline | the client's result |
| what you deliver and when | adoption by their team |
| rework within the written scope | the client's revenue growth |
| returning the difference against an agreed metric | their market improving |

**Test before promising:** *"does this depend on something I do not control?"* If yes, rewrite the promise as a process, not as a result. For guarantees, use the exposure mathematics (`references/02-offer-and-pricing.md`).

## 1.5 The profile file — prerequisite for everything

**Where:** `templates/business-profile.md`, filled in once.
**Why:** without it, every output degrades into generic advice. This is the central conclusion of the best business-skill collections: a context file read by every skill and owned by none.

**Minimum acceptable before producing anything:**

| Field | Why it is indispensable |
|---|---|
| what you sell, in one sentence | defines the offer |
| ideal client (segment, size, role) | defines target and message |
| main pain, in the client's words | defines narrative and implication |
| client's current alternative (including "do nothing") | defines price anchoring |
| available proof (number of clients, authorised cases) | defines what you can claim |
| current prices and tiers | defines the pricing analysis |
| your delivery capacity | avoids selling what you cannot deliver |

**If the profile is not filled in:** do not invent the context. Ask the user **only** the questions in this table, once, and record the answers in the profile before proceeding.

## 1.6 How the profile is used (and not used)

- Deliverables **read** the profile and **never** overwrite it on their own.
- Switching client or project = switching the file. The methodology stays.
- A blank field in the profile does **not** become an assumption: it becomes a question or `[to fill in]`.
